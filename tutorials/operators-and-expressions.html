01Operators, operands, and expressions

An operator is a symbol or keyword that tells the compiler to perform one specific action. The values it acts upon are its operands. Any valid combination of operands and operators is an expression, and every expression produces a value.

int a = 5, b = 3;
int c = a + b;   /* '+' is the operator, 'a' and 'b' are operands,
                    'a + b' is an expression whose value is 8    */

Three ideas run through this entire tutorial:

Value

Every expression evaluates to a value of a definite type. Only void expressions produce no value.

Side effect

Some expressions also change program state: assignment, ++, --, and function calls that modify data or perform input and output.

Evaluation order is a separate rule

C's rules decide which operand belongs to which operator through precedence and associativity. In most cases they do not decide the order in which the operands are actually computed. Sections 10 through 16 build this distinction carefully; it is the origin of most expression bugs.

Expression statements

Adding a semicolon to an expression turns it into a statement.

x = 10;         /* assignment expression used as a statement    */
i++;            /* increment expression used as a statement     */
printf("hi");   /* function-call expression used as a statement */
3 + 4;          /* legal but useless: 7 is computed and discarded */

The last line compiles because C evaluates the expression and simply throws the value away. This "everything is an expression" design explains why an assignment can appear inside a condition, why the comma operator exists, and why side effects deserve a section of their own.

Bitwise operators

These act on the individual bits of integer operands.

OperatorMeaningExample with a = 12 (1100), b = 10 (1010)
&Bitwise ANDa & b gives 8 (1000)
|Bitwise ORa | b gives 14 (1110)
^Bitwise XORa ^ b gives 6 (0110)
~Bitwise NOT~a gives −13 on two's-complement machines
<<Left shifta << 1 gives 24
>>Right shifta >> 1 gives 6
The shift count is not a free integer

In a << b and a >> b, the right operand b must satisfy 0 <= b < N, where N is the bit width of the promoted left operand. A negative count, or a count equal to or greater than that width, is undefined behavior — not a shift in the opposite direction, and not a guaranteed zero.

int a = 12;

a << -1;   /* negative count                      */
a >> -1;   /* negative count, same rule for >>     */
a << 32;   /* count equals the width of a 32-bit int */
a << 40;   /* count exceeds the width               */

These produce nonsense rather than a diagnostic at run time. On one tested x86-64 machine, 12 << -1 evaluated to 0 and 12 << 32 evaluated to 12, unchanged, because the hardware quietly kept only the low bits of the count. Another processor, or the same one after optimisation, may do something entirely different.

Two related rules complete the picture:

  • A negative left operand of << is also undefined. -12 << 1 happens to give -24 here, but the standard does not permit relying on it. Shift unsigned values when you are working with bit patterns.
  • A negative left operand of >> is implementation-defined, not undefined. Every common compiler copies the sign bit, so -12 >> 1 gives -6, but the standard allows an implementation to shift in zeros instead.

Keep the count in a checked range, and turn on -Wall: both GCC and Clang report shift count is negative and shift count >= width of type whenever the count is a constant.

The width is the promoted width

Integer promotion runs before the shift, so a char or short left operand becomes an int first, and the limit is int's width rather than the original type's. With a 16-bit short h = 1, the expression h << 20 is valid and gives 1048576. The limit rises again for long long, where counts up to 63 are permitted.

Keep the two families apart

& and | are bitwise operators that always evaluate both operands. && and || are logical operators that stop early. A single missing character changes both the meaning and the safety of a condition.

The cast operator in practice

Because integer division truncates, a cast is what rescues an average or a ratio.

int sum = 17, n = 5;

float wrong = sum / n;         /* 3.0: integer division happened first */
float right = (float)sum / n;  /* 3.4: sum becomes float, so does the
                                  whole division                        */
Why the cast must come first

In (float)(sum / n) the truncation already happened before the conversion, so the result is still 3.0. Cast one operand, not the finished result.

03Lvalues and rvalues

Some operators need more than a value. =, ++, and & need to know where a value lives, because they must store into that place or take its address. C splits expressions into two categories to express this.

Lvalue

An expression that designates an object, meaning a named region of storage. It has a location, so it can be read from and, usually, written to.

Rvalue

An expression that produces only a value, with no storage location you can name. It can be read, and nothing more.

Where the names come from

Historically, an lvalue is what may appear on the left of an assignment and an rvalue is what may appear on the right. Treat that as a mnemonic only. The accurate reading of the l is locator: an lvalue locates an object. Every lvalue can also be used on the right-hand side, so the two categories are not symmetric.

Modifiable and non-modifiable lvalues

Having a location is not the same as being writable. An lvalue is modifiable unless it is const-qualified or has array type.

Assignment yields a value, not a place

In C the result of a = b is an rvalue: the value that was stored. This is why (a = b) = c and &(a = b) are both errors. C++ made assignment produce an lvalue instead, which is a common source of confusion when reading code from the other language.

                   has no object to work on              */

The classic typo has an lvalue explanation

Writing if (x = 5) instead of if (x == 5) compiles because x is a modifiable lvalue, so the assignment is legal. Reversing the operands as if (5 == x) turns the same typo into 5 = x, which is an immediate lvalue error. That is the entire reason behind the so-called Yoda condition style in Section 16.

Reading an lvalue converts it to a value

In most contexts an lvalue is immediately read, and what the surrounding expression sees is the value stored there. This step is called lvalue conversion.

int a = 3, b = 4, c;

c = a + b;   /* a and b are lvalues, but each is read for its value.
                c stays an lvalue, because '=' stores into it.       */

The four contexts that do not perform this conversion are precisely the ones that need the location itself: the left operand of an assignment, the operand of &, the operand of ++ or --, and the operand of sizeof.

Carry this into the next sections

Every rule about op= in Section 04, about ++ and -- in Sections 05 and 06, and about side effects in Section 15 rests on this one idea: those operators act on an object, and an expression that merely produces a value has no object for them to act on.

04Compound assignment operators

A compound assignment merges a binary operation with an assignment.

lhs op= rhs is almost the same as lhs = lhs op (rhs)

There are ten of them: +=, -=, *=, /=, %=, &=, |=, ^=, <<=, >>=.

int i = 10;

i += 5;   /* i = i + 5  ->  15 */
i -= 3;   /* i = i - 3  ->  12 */
i *= 2;   /* i = i * 2  ->  24 */
i /= 5;   /* i = i / 5  ->  4, integer division */
i %= 3;   /* i = i % 3  ->  1  */

Why it is more than a shorthand

The word "almost" in the equivalence above hides two real guarantees.

The left side is evaluated once

a[f()] += 1;

f() is called exactly once, so exactly one element is read and updated.

The long form evaluates it twice

a[f()] = a[f()] + 1;

f() is called twice and may return two different indexes, updating the wrong element.

This matters whenever the left side has a side effect or is expensive to compute.

The right side is implicitly parenthesised

int x = 10;
x *= 3 + 2;   /* x = x * (3 + 2) = 50,  NOT (x * 3) + 2 = 32 */

The whole right-hand expression is computed first, and only then combined with the left side.

Type conversion still applies

The result is converted to the type of the left operand, exactly as in a simple assignment.

int i = 7;
i /= 2.0;    /* computed as 7 / 2.0 = 3.5 in double,
                then truncated on storage: i is 3 */

char c = 100;
c += 50;     /* the arithmetic happens in int and produces 150,
                which is then stored back into a char           */

A compound assignment is an expression

int x = 3, y;
y = (x += 5);   /* x becomes 8, and y also becomes 8 */
Style

Prefer count += step; over count = count + step;. It states the intent, adjust in place, and removes the risk of retyping the wrong variable name. Keep compound assignments as standalone statements rather than burying them inside larger expressions.

05Prefix versus postfix increment

Both ++x and x++ add 1 to x. They differ only in the value the expression itself produces.

FormValue of the expressionSide effect
++x, pre-incrementThe value of x after the incrementx increases by 1
x++, post-incrementThe value of x before the incrementx increases by 1
The position of ++ tells you when it happens: before the variable means change then use, after the variable means use then change.

Side-by-side

int x, y;

x = 5;
y = ++x;   /* x becomes 6 first, then y = 6.  Now x == 6, y == 6 */

x = 5;
y = x++;   /* y takes the old value 5, then x becomes 6.  x == 6, y == 5 */

Alone, the two forms are identical

When the value of the expression is discarded, nothing distinguishes them.

i++;                              /* same net effect */
++i;                              /* same net effect */

for (i = 0; i < 10; i++) { ... }  /* identical loop behavior */
for (i = 0; i < 10; ++i) { ... }  /* identical loop behavior */

Inside a larger expression, the difference decides the answer

int a = 3, b = 3;

int p = 10 * a++;   /* p = 10 * 3 = 30; afterwards a == 4 */
int q = 10 * ++b;   /* b becomes 4 first, so q = 10 * 4 = 40 */

The same distinction appears in the classic array idiom.

int arr[5] = {10, 20, 30, 40, 50};
int i = 1;

int v1 = arr[i++];   /* v1 = arr[1] = 20, then i becomes 2 */
int v2 = arr[++i];   /* i becomes 3 first, so v2 = arr[3] = 40 */
arr[0]10 
arr[1]20i++ reads here
arr[2]30 
arr[3]40++i reads here
arr[4]50 

Starting from i == 1, the postfix form subscripts with the old index while the prefix form subscripts with the new one.

What the operand is allowed to be

  • The operand must be a modifiable lvalue: a variable, an array element, a dereferenced pointer, or a structure member. 5++ and (a + b)++ are compile errors because neither designates an object.
  • ++ cannot be stacked: ++x++ is illegal because x++ produces a value rather than an object, so the outer ++ has nothing to increment.
A more precise statement of timing

Formally, x++ produces the old value and the increment is applied at some point before the next sequence point, not necessarily the instant the value is read. That looseness is exactly why x++ + x++ is undefined, as Section 16 shows. For a single, isolated use, the simple "use then increment" picture is safe.

06Prefix versus postfix decrement

The decrement operator mirrors ++ exactly, subtracting 1 instead of adding it.

FormValue of the expressionSide effect
--x, pre-decrementThe value of x after subtracting 1x decreases by 1
x--, post-decrementThe value of x before subtracting 1x decreases by 1
 
int x, y;

x = 5;
y = --x;   /* x becomes 4 first, so y == 4 and x == 4 */

x = 5;
y = x--;   /* y takes the old value 5, then x becomes 4 */

Countdown loops make the difference visible

int n = 5;
while (n > 0) {
    printf("%d ", n--);   /* prints the old value, then decrements */
}
printf("\n");

int m = 5;
while (m > 0) {
    printf("%d ", --m);   /* decrements first, then prints */
}
printf("\n");
5 4 3 2 1 4 3 2 1 0

Both loops terminate correctly, yet the choice of form changed the observable output.

A combined trace

int a = 8, b = 3, result;
result = a-- - --b;
StepWhat happensContributesState after
1--b subtracts first2b == 2
2a-- supplies the old value8a == 7
3subtraction8 - 2result == 6

The two operands here are different variables, so this expression is completely well defined. Section 16 shows what goes wrong when they are the same variable.

Whitespace is not optional here

a-- - --b is correct, but a-----b is a syntax error. The tokenizer takes the longest operator it can at each step and reads a-- -- -b, and a-- cannot be decremented again. Always separate consecutive operator characters with a space.

07The conditional operator

The conditional operator is C's only ternary operator. It packs an if/else choice of values into a single expression.

condition ? value_if_true : value_if_false

Evaluation follows a guaranteed order:

  1. The condition is evaluated.
  2. If it is nonzero, only the true branch is evaluated and its value becomes the result.
  3. If it is zero, only the false branch is evaluated and its value becomes the result.

Exactly one branch ever runs. Side effects prove it.

int i = 0, j = 0;

int x = (1 ? i++ : j++);   /* condition true, so only i++ runs  */
printf("%d %d\n", i, j);

int y = (0 ? i++ : j++);   /* condition false, so only j++ runs */
printf("%d %d\n", i, j);
1 0 1 1

That guarantee is what makes the operator safe as a guard.

int    len = (p != NULL) ? p->length : 0;
double avg = (n != 0) ? (double)sum / n : 0.0;

Basic examples

int a = 10, b = 25;
int max = (a > b) ? a : b;        /* max == 25 */

int n = -7;
int abs_n = (n < 0) ? -n : n;     /* abs_n == 7 */

printf("You have %d item%s\n", k, (k == 1) ? "" : "s");

Relationship to if/else

Conditional expression

max = (a > b) ? a : b;

Equivalent statement

if (a > b)
    max = a;
else
    max = b;

The difference is that ?: is an expression, so it can appear in places where a statement cannot: initializers, function arguments, array subscripts, and inside other expressions.

int table_size = (n > 100) ? 211 : 47;
printf("%d\n", (x % 2 == 0) ? x / 2 : 3 * x + 1);

Nesting reads like an else-if ladder

The conditional operator associates right to left, which makes a cascade possible.

grade = (score >= 90) ? 'A'
      : (score >= 80) ? 'B'
      : (score >= 70) ? 'C'
      : (score >= 60) ? 'D'
      :                 'F';

This layout is good style. A one-line version such as a?b?c:d:e?f:g is legal but unreadable and should be avoided.

Precedence and the type of the result

?: has very low precedence, just above assignment and comma, so surrounding arithmetic usually groups as expected. Assignments inside the branches are the exception.

x = (a > b) ? a : b;         /* fine: ?: binds tighter than = */

(a > b) ? x = a : (x = b);   /* legal but awkward; the parentheses on
                               the last branch are required          */

Both branches are converted to a common type by the usual arithmetic conversions.

double d = (flag) ? 1 : 2.5;   /* branches are int and double, so the
                                  result type is double: 1.0 or 2.5   */
Rule of thumb

Use ?: to select a value. If both branches are assignments or function calls, write an if statement instead.

08The comma operator

The comma operator evaluates two expressions in order and produces the value of the second.

expr1 , expr2 → evaluate expr1 and discard it, then evaluate expr2

It has the lowest precedence of every C operator, and it guarantees left-to-right order with a sequence point between the operands, so all side effects of expr1 finish before expr2 begins.

Its value, and a precedence surprise

int x;

x = (3, 5);   /* x == 5: 3 is evaluated and thrown away */
x = 3, 5;     /* x == 3: parsed as (x = 3), 5 because the comma
                 has lower precedence than assignment        */

Where the comma operator belongs: for headers

Its natural home is a loop that must advance two variables inside the three slots of a for header.

/* Reverse an array in place with two indexes moving toward each other */
for (i = 0, j = n - 1; i < j; i++, j--) {
    int tmp = a[i];
    a[i] = a[j];
    a[j] = tmp;
}

Operator versus separator

The same character plays two unrelated roles, and only one of them is the operator.

CodeRole of the comma
int a, b, c;Separator in a declaration
f(x, y, z);Separator between arguments
f((x, y), z);The inner comma is the operator: f receives the value of y and then z
int arr[3] = {1, 2, 3};Separators in an initializer list
The guarantee does not transfer

Because argument commas are separators and not the operator, the order in which f(g(), h()) evaluates g() and h() is unspecified. The left-to-right promise belongs to the comma operator only.

Outside for headers and the occasional compact macro, the comma operator hurts readability. x = 1, y = 2, z = 3; is legal, but three separate statements are clearer.

09The sizeof operator

sizeof is a unary, compile-time operator that produces the size in bytes of a type or of an expression's type. Its result has the unsigned type size_t, declared in <stddef.h> and printed with %zu.

Two syntactic forms

sizeof (type-name)   /* parentheses are REQUIRED around a type name */
sizeof expression    /* parentheses are optional around an expression */

sizeof (int);        /* first form  */
sizeof x;            /* second form, legal without parentheses */
sizeof (x);          /* also legal; many programmers always parenthesize */

Typical sizes, which are implementation-dependent

The standard fixes only minimums and relationships. Real sizes vary by machine and compiler. On a typical 64-bit desktop system:

TypeTypical size in bytes
char1, and this one is guaranteed
short2
int4
long8, but often 4 on 64-bit Windows
long long8
float4
double8
any pointer8
sizeof(char) <= sizeof(short) <= sizeof(int) <= sizeof(long) <= sizeof(long long)

The operand is not evaluated

int i = 5;
size_t s = sizeof(i++);   /* s is sizeof(int), and i is STILL 5:
                             the expression is only type-checked */

Because only the type is needed, the operand never runs. The single exception, variable-length arrays, is outside the scope of this lesson.

The element-count idiom

For a true array, sizeof gives the whole array's byte count.

int data[25];

size_t nbytes    = sizeof data;                  /* 25 * sizeof(int) = 100 */
size_t nelements = sizeof data / sizeof data[0]; /* 25 elements */
The idiom stops working inside a function

When an array is passed to a function it decays to a pointer, so sizeof then reports the pointer's size instead of the array's.

void f(int a[]) {
    /* sizeof a is sizeof(int *), for example 8, not 100 */
}

Always pass the element count as a separate parameter.

Practical uses

/* Portable allocation: adapts automatically if p's type changes */
int *p = malloc(n * sizeof *p);

/* Portable input and clearing */
fread(buffer, sizeof buffer[0], n, fp);
memset(&record, 0, sizeof record);

10Operator precedence

Precedence decides which operator takes its operands first when an expression mixes different operators. It answers how the expression is implicitly parenthesised, and nothing else.

a + b * c   /* means a + (b * c), because * outranks + */
a * b + c   /* means (a * b) + c */

The full table, highest level first

The highlighted rows are the three levels that surprise almost everyone: the bitwise operators bind more loosely than the comparisons.

Four landmarks worth memorising

  • Unary beats binary: -a * b is (-a) * b.
  • Arithmetic beats relational beats logical, so a + 1 > b && c < d parses as ((a + 1) > b) && (c < d) with no parentheses required.
  • Assignment sits near the bottom, so everything on its right is computed before the store happens.
  • The comma operator is dead last.

Worked evaluations

int a = 2, b = 3, c = 4, r;

r = a + b * c;        /* a + (b*c)        = 2 + 12  = 14 */
r = (a + b) * c;      /* (2+3) * 4                  = 20 */
r = a * b % c;        /* same level, left to right:
                         (a*b) % c        = 6 % 4   = 2  */
r = -a * b;           /* (-a) * b                   = -6 */
r = a < b == c > b;   /* (a<b) == (c>b)  = 1 == 1  = 1  */
r = a & b == 2;       /* a & (b == 2)    = 2 & 0   = 0  */

The last line is the surprise: == is evaluated first, so the mask is ANDed with a truth value rather than with 2.

Four precedence traps

Trap 1 · Bitwise against equality
if (flags & MASK == 0)     /* WRONG: parsed as flags & (MASK == 0) */
if ((flags & MASK) == 0)   /* RIGHT */
Trap 2 · Shift against addition
x << 2 + 1     /* means x << 3, because + outranks << */
(x << 2) + 1   /* what was probably intended */
Trap 3 · Assignment inside a condition
while ((ch = getchar()) != EOF)   /* the inner parentheses are essential:
                                     != outranks =, so without them this
                                     becomes ch = (getchar() != EOF)   */
Trap 4 · Dereference against member access
*p.x     /* means *(p.x), which is usually an error */
(*p).x   /* dereference first, then take the member */
p->x     /* the idiomatic form of (*p).x            */
What precedence does not tell you

Precedence fixes grouping only. In f() + g() * h() it guarantees that the product is added to f()'s result, but the three calls may run in any order. Run-time evaluation order is a separate concept, handled in Section 16.

11Operator associativity

When two operators from the same precedence level compete for the same operand, associativity breaks the tie.

Left-to-right associativity

Most binary operators group from the left. Subtraction and division make this visible because they are not mathematically associative.

a - b - c        /* means (a - b) - c */
100 - 20 - 5     /* (100-20)-5 = 75, not 100-(20-5) = 85 */

a / b / c        /* means (a / b) / c */
100 / 10 / 5     /* (100/10)/5 = 2, not 100/(10/5) = 50 */

a - b + c        /* same level, so (a - b) + c */

Right-to-left associativity

Three groups associate from the right: unary operators, ?:, and assignments.

a = b = c = 0;   /* grouped as a = (b = (c = 0));
                    c gets 0, that expression's value 0 goes to b,
                    and then to a. All three become 0.            */

x = y += 2;      /* grouped as x = (y += 2) */

The chain works because each assignment is an expression whose value is what was stored, and that value feeds the assignment to its left.

!!x           /* !(!x) turns any nonzero value into exactly 1 */
- -x          /* -(-x) == x; note the space, since --x is decrement */
*&a           /* *(&a) == a */
(int)(float)n /* casts apply right to left */

Conditional chains follow the same rule: a ? b : c ? d : e means a ? b : (c ? d : e), which is what makes the else-if cascade of Section 07 read correctly.

Why mixed-direction expressions still parse

x = a + b + c;

/* '+' groups from the left:  (a + b) + c
   '=' groups from the right: x = ((a+b)+c)
   The two never conflict, because associativity only
   arbitrates within a single precedence level.        */
Associativity is still not evaluation order

a() + b() + c() groups as (a() + b()) + c(), yet the compiler is free to call c() first. Like precedence, associativity fixes the parse tree, not the run-time schedule. Only &&, ||, ?:, and , fix the schedule.

12Parentheses and explicit grouping

Parentheses override precedence and associativity. Whatever is inside is grouped as a unit first.

2 + 3 * 4        /* 14 */
(2 + 3) * 4      /* 20 */

a = 100 / 10 * 2;      /* (100/10)*2 = 20 */
a = 100 / (10 * 2);    /* 100/20     = 5  */

The classic temperature conversion shows why this matters in real code.

fahr = 9 / 5 * c + 32;       /* BUG: 9/5 is 1 in integer arithmetic */
fahr = 9.0 / 5.0 * c + 32;   /* fixed with floating constants       */
fahr = (9 * c) / 5 + 32;     /* fixed by regrouping: multiply first */

Nesting, and where parentheses are mandatory

Innermost pairs group first, and there is no practical limit on depth.

result = ((a + b) * (c - d)) / (e + 1);

Some contexts require parentheses no matter what the precedence table says: the controlling expression of if, while, for, and switch; function-call argument lists; sizeof(type); and casts written as (type)expr.

Parentheses written for the reader

Correct but demanding

if (a > 0 && b > 0 || c > 0 && d > 0)

The reader has to recall three precedence levels to be sure what this means.

Same meaning, immediately clear

if ((a > 0 && b > 0) || (c > 0 && d > 0))

The grouping is stated instead of implied.

  • Parenthesize whenever && and || appear together.
  • Parenthesize every bitwise sub-expression that meets a comparison.
  • Parenthesize the condition of a ?: used inside a larger expression.
  • Do not parenthesize into noise. ((a) + (b)) helps nobody.
What parentheses cannot do

They control grouping, never run-time order. In (f() + g()) + h() the compiler may still call h() before f() or g(). To force an order, use separate statements.

13Compound conditions

Real programs rarely test one thing at a time. A compound condition joins relational tests with &&, ||, and !.

pqp && qp || q!p

01011

11110

Building them

/* Is x inside the range [low, high]? */
if (x >= low && x <= high) ...

/* Is x outside it? */
if (x < low || x > high) ...

/* Leap year: divisible by 4, except centuries, except every 400th year */
if ((year % 4 == 0 && year % 100 != 0) || (year % 400 == 0))
    printf("%d is a leap year\n", year);

/* Do three lengths form a valid triangle? */
if (a + b > c && b + c > a && a + c > b) ...

/* Character classification by hand */
if ((ch >= 'a' && ch <= 'z') || (ch >= 'A' && ch <= 'Z')) ...

The mathematics-notation trap

Chained comparison
if (0 <= x && x <= 10)   /* correct */
if (0 <= x <= 10)         /* compiles, but is ALWAYS TRUE */

The second line parses as (0 <= x) <= 10. The left half produces 0 or 1, and both are less than or equal to 10, so the test can never fail.

Negating a compound condition

!(p && q) is !p || !q · !(p || q) is !p && !q
if (!(x >= 0 && x < n))   /* "not a valid index" */
if (x < 0 || x >= n)       /* the same test, usually clearer */

Every relational test also has a direct negation: !(a < b) is a >= b, and !(a == b) is a != b. Prefer the direct form over a leading !.

Precedence inside conditions

Relational operators outrank &&, which outranks ||.

a < b && c < d || e < f
/* parses as ((a < b) && (c < d)) || (e < f) */

AND binds more tightly than OR, just as multiplication binds more tightly than addition in algebra.

Truth values are ordinary integers

Because a comparison yields 0 or 1, comparisons can be counted.

int passes = (s1 >= 60) + (s2 >= 60) + (s3 >= 60);   /* 0 to 3 */

Occasionally useful, and worth recognising when reading other people's code.

14Short-circuit evaluation

&& and || are special. They evaluate left to right and they stop as soon as the answer is known.

ExpressionBehavior
p && qEvaluate p. If it is 0, the result is 0 and q is never evaluated.
p || qEvaluate p. If it is nonzero, the result is 1 and q is never evaluated.

There is a sequence point after the left operand, so all of its side effects finish before the right operand starts, if it starts at all.

int i = 0, j = 0;

if (i > 0 && ++j > 0) { }   /* i > 0 is false, so ++j never runs */
printf("%d\n", j);

i = 1; j = 0;
if (i > 0 || ++j > 0) { }   /* the left side is true, so ++j never runs */
printf("%d\n", j);
0 0

The guard idiom

The most important practical use is to make the left operand a safety check that protects the right one.

/* Divide only when the divisor is nonzero */
if (n != 0 && total / n > threshold) ...

/* Dereference only a valid pointer */
if (p != NULL && p->count > 0) ...

/* Check the index before using it */
if (i >= 0 && i < n && a[i] == key) ...
Order is part of the meaning

Reversing the operands in any of the three lines above would risk a division by zero, a null dereference, or an out-of-bounds read. In a short-circuit expression, put the guard first.

When both operands are safe, put the cheaper or more decisive test first for speed.

if (count > 0 && expensive_lookup(key)) ...   /* skips the lookup when count is 0 */

The flip side: skipped side effects

if (x > 0 && y++ > 5) ...   /* y++ happens ONLY when x > 0.
                               Is that really what was intended? */

Keep the operands of && and || free of side effects, except for well-known idioms where the effect is the whole point of the call.

The bitwise forms do not short-circuit
if ((p != NULL) & (p->len > 0))    /* DANGER: both sides always run,
                                      so this crashes when p is NULL */
if ((p != NULL) && (p->len > 0))   /* safe */

One missing character changes a safe guard into a crash.

15Side effects inside expressions

A side effect is any change to program state that happens while an expression is being evaluated: modifying a variable with =, op=, ++, or --; performing input or output; or calling a function that does either.

y = (x = 5) + 2;        /* effect: x becomes 5. Value of (x=5) is 5, so y == 7 */
n = i++;                /* effect: i is incremented. Value: the old i */
m = printf("hello\n");  /* effect: output. Value: the number of characters, 6 */

Idioms that are built on side effects

Some C idioms exploit expression side effects deliberately, and they are good style precisely because every C programmer recognises them.

/* Read and test in one condition */
while ((ch = getchar()) != EOF)
    process(ch);

/* Copy a string, the classic loop */
while ((*dst++ = *src++) != '\0')
    ;

/* Allocate and check together */
if ((p = malloc(size)) == NULL)
    handle_error();

When side effects turn toxic

Trouble begins when one expression contains two side effects on the same variable, or a side effect on a variable plus a separate read of that same variable.

i = 5;

k = i++ + i;   /* does the second i see 5 or 6?  UNDEFINED BEHAVIOR */
a[i] = i++;    /* which element is assigned?      UNDEFINED BEHAVIOR */
x = x++;       /* two unsequenced writes to x:    UNDEFINED BEHAVIOR */
Undefined is stronger than unpredictable

These are not merely compiler-dependent. The standard says such a program has undefined behavior, which permits any result at all, including a crash or silent corruption elsewhere in the program.

Sequence points: where effects are settled

A sequence point is a moment at which every earlier side effect is complete and no later one has begun. The ones you need are:

  1. The end of a full expression, that is, the semicolon.
  2. After the left operand of &&, ||, and the comma operator.
  3. After the condition of ?:.
  4. After all arguments of a function call are evaluated, before the body runs.
  5. At the end of each initializer and each controlling expression of if, while, or a for clause.
Between two sequence points a variable may be modified at most once,
and if it is modified, its old value may be read only to compute the new one.

Breaking either half of that rule is undefined behavior.

Practical discipline

  • One side effect per statement is a robust default.
  • Let ++ and -- stand alone, as in i++;, or appear once in a simple idiom such as a[i++] = v;.
  • Never mention a variable elsewhere in an expression that increments it.
  • Reserve assignment-inside-a-condition for the classic idioms above, always parenthesised and compared explicitly.

16Evaluation-order pitfalls

This section gathers the sharp edges of Sections 10 through 15 into one safety briefing.

Three concepts that must stay separate

ConceptQuestion it answersExample guarantee
PrecedenceWhich operator binds more tightly?a + b*c is a + (b*c)
AssociativityHow do equal-precedence operators group?a-b-c is (a-b)-c
Evaluation orderWhen is each operand actually computed?Mostly unspecified

For most operators C deliberately leaves operand order to the compiler so it can optimise. Only &&, ||, ?:, and the comma operator promise left-to-right evaluation.

Unspecified order: calls and subexpressions

int f(void) { printf("f "); return 1; }
int g(void) { printf("g "); return 2; }

int r = f() + g();             /* may print "f g " or "g f " */
printf("%d %d\n", f(), g());   /* argument order is also unspecified */

The value of f() + g() is a well-defined 3. The output order is not. When order matters, sequence the calls yourself.

int x = f();
int y = g();
int r = x + y;   /* the order is now explicit and guaranteed */

Undefined behavior: the modify-and-read family

These are the classic exam traps. None of them has an answer to work out.

i = i++ + ++i;             /* undefined */
printf("%d %d", i, i++);   /* undefined: i is read and modified, unsequenced */
a[i] = i++;                /* undefined */
f(i++, i);                 /* undefined */
x = x++ + 1;               /* undefined */
There is no correct answer to compute

Different compilers, and even the same compiler at different optimisation levels, legitimately produce different results. If a quiz asks what i++ + ++i prints, the only correct response is that the program is invalid. Contrast this with k = a-- - --b; from Section 06, which modifies two different variables and is perfectly well defined.

Why the macro row deserves its own warning

#define SQUARE(x) ((x) * (x))

int i = 3;
int s = SQUARE(i++);   /* expands to ((i++) * (i++)): undefined, and i
                          advances twice even when the result "looks right" */

Function-like macros silently duplicate their arguments. Never feed them an expression with a side effect.

Rules for writing unambiguous expressions

  1. One side effect per statement. Split anything more complex.
  2. Never modify and separately read the same variable in one expression.
  3. Never let two function calls with observable effects share one expression when their order matters. Sequence them as separate statements.
  4. Parenthesize whenever && meets ||, whenever a bitwise operator meets a comparison, and whenever a shift meets arithmetic.
  5. Put the guard first in a short-circuit condition and keep the right side free of side effects.
  6. Use == consciously. Some programmers write if (5 == x) so that a missing character becomes a compile error rather than a silent bug.
  7. Prefer clarity over cleverness. i++; j = a[i]; costs nothing over j = a[++i]; and can never be misread.
  8. Turn compiler warnings on. With GCC or Clang, -Wall -Wextra flags assignments inside conditions, unparenthesised precedence hazards, and many sequencing bugs.

Prefix and postfix in one box

x = 5;  y = ++x;   /* y == 6, x == 6 : change, then use */
x = 5;  y = x++;   /* y == 5, x == 6 : use, then change */
x = 5;  y = --x;   /* y == 4, x == 4 */
x = 5;  y = x--;   /* y == 5, x == 4 */

Eight rules to carry away

  1. =, op=, ++, and -- need a modifiable lvalue; & needs an lvalue. Everything else works on values.
  2. Precedence is grouping. Associativity is tie-breaking. Neither is run-time order.
  3. Only &&, ||, ?:, and , promise an evaluation order.
  4. Modify a variable at most once per expression, and do not read it elsewhere in that expression.
  5. Parentheses cost nothing. Spend them at the boundaries between operator families.
  6. sizeof is resolved at compile time and its operand never runs.
  7. Integer arithmetic truncates. Cast one operand before dividing when you want a fraction.
  8. = assigns and == compares; & masks bits and && guards logic.

18Practice and quick checks

Work each problem on paper before opening the solution.

Exercise 1 With int a = 10, b = 3; evaluate a / b, a % b, a / b * b + a % b, and (float)a / b.

Show solution

a / b is 3 because integer division truncates. a % b is 1. The third expression is 3 * 3 + 1, which is 10: the division identity recovers a. The fourth is 3.333… because the cast forces real division.

Exercise 2 What are x, y, and z after this fragment?

int x = 4, y, z;
y = x++ * 2;
z = ++x * 2;
Show solution

x++ supplies 4, so y = 8 and x becomes 5. Then ++x makes x 6 before the multiplication, so z = 12. Final state: x == 6, y == 8, z == 12.

Exercise 3 Parenthesize according to C's rules, without evaluating: a = b < c && d == e || !f

Show solution
a = ((((b < c) && (d == e))) || (!f))

Unary ! binds first, then <, then ==, then &&, then ||, with the assignment last.

Exercise 4 With int i = 3, j = 8; what does k = (i > j) ? i-- : j--; leave in i, j, and k?

Show solution

The condition is false, so only j-- is evaluated. k receives the old value 8 and j becomes 7. i is never touched. Final state: i == 3, j == 7, k == 8.

Exercise 5 How many times does check() run, and what is printed?

int check(void);   /* returns 0 or 1 */

if (0 && check()) puts("A");
if (1 || check()) puts("B");
Show solution

Zero times. The left operand of && is false, so its right side is skipped; the left operand of || is true, so its right side is skipped. The output is B.

Exercise 6 What is printed, and why is no increment performed?

int n = 10;
printf("%zu %d\n", sizeof(n++), n);
Show solution

The operand of sizeof is not evaluated, only type-checked. The line prints the size of int, typically 4, followed by 10.

Exercise 7 Explain the bug in if (grade = 100) printf("Perfect!");

Show solution

= assigns. grade is overwritten with 100, the expression's value is 100, which is true, so the message always prints and the original grade is lost. The intended test is grade == 100.

Exercise 8 With int i = 2, j = 5, k; classify each as well defined or undefined, and give the values where they are defined.

(a) k = i++ + j++;
(b) k = i++ + i;
(c) k = (i++, i + j);
(d) i = i + 1;
Show solution

(a) Defined, because the two side effects hit different variables: k = 2 + 5 = 7, then i == 3 and j == 6.

(b) Undefined. i is modified and independently read in the same expression.

(c) Defined. The comma operator places a sequence point between the effects: i becomes 3 first, so k = 3 + 5 = 8.

(d) Defined. The read of i exists only to compute its new value, which is exactly what the rule permits: i becomes 3.

Exercise 9 Rewrite without the bug: if (temp >= 60 <= 90) run();

Show solution

(temp >= 60) produces 0 or 1, and both are less than or equal to 90, so the condition is always true. The correct test is if (temp >= 60 && temp <= 90) run();

Exercise 10 Using only ?:, write an expression for the median of three distinct values a, b, and c.

Show solution
mid = (a > b) ? ((b > c) ? b : (a > c) ? c : a)
               : ((a > c) ? a : (b > c) ? c : b);

The outer test orders a against b, and each branch then places c relative to that pair.

Exercise 11 Given int a = 1, b = 2, arr[3]; int *p = &a; const int c = 9; mark each expression as a modifiable lvalue, a non-modifiable lvalue, or an rvalue, and say which of them may legally appear on the left of =.

(i)   a
(ii)  arr
(iii) arr[1]
(iv)  *p
(v)   c
(vi)  a + b
(vii) (a)
(viii) a++
Show solution

Modifiable lvalues, all legal on the left of =: (i) a, (iii) arr[1], (iv) *p, and (vii) (a), since parentheses never change lvalue status.

Non-modifiable lvalues, illegal on the left of = but legal as the operand of &: (ii) arr, because it has array type, and (v) c, because it is const-qualified.

Rvalues: (vi) a + b and (viii) a++. Both produce a value with no designated object, so neither can be assigned to, incremented, or given to &.

Exercise 12 With int x = 12; on a machine where int is 32 bits, which of these are valid, and what is wrong with the rest?

(i)   x << 3
(ii)  x << -2
(iii) x >> 31
(iv)  x << 32
(v)   -x << 1
(vi)  -x >> 1
Show solution

Valid: (i) x << 3 gives 96, and (iii) x >> 31 gives 0. Both counts lie in the required range 0 to 31.

Undefined: (ii) the count is negative; (iv) the count equals the 32-bit width, and the limit is one less; (v) the left operand of << is negative.

(vi) is implementation-defined rather than undefined. Every common compiler copies the sign bit and produces -6, but the standard does not require it. Shift unsigned values whenever the bit pattern is what matters.

Final mental model

An operator combines operands into an expression that has both a value and, sometimes, a side effect. Precedence and associativity decide only how the expression is grouped. Evaluation order is a separate promise that C makes for just four operators. Write each expression so that its meaning does not depend on the promises C never made.
